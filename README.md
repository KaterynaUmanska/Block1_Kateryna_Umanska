
# Система агрегації статистики за закупівлями (Java Core)

Консольна багатопотокова програма на Java для потокового парсингу JSON-файлів із купівельними заявками, обчислення статистики за вказаним атрибутом та генерації відсортованого XML-звіту.

---

## 1. Опис основних сутностей

Проєкт побудований на принципах об'єктно-орієнтованого програмування та демонструє зв'язок між сутностями:

* **PurchaseRequisition (Заявка на закупівлю)** - основна сутність, що містить інформацію про закупівлю. Поля: `id` (Long), `material` (`Material` - вкладений об'єкт), `quantity` (Double), `status` (`Status` - Enum: DRAFT, IN_APPROVAL, APPROVED, CANCELED), `tags` (String - текстові теги через кому).

* **Material (Матеріал)** - другорядна сутність. Поля: `id` (Long), `name` (String), `unit` (`Unit` - Enum: KG, PCS, METERS, LITERS), `description` (String).

> **Зв'язок між сутностями:** Many-to-One - багато заявок на закупівлю можуть бути пов'язані з одним матеріалом.

Для спрощення предметної області в межах даного завдання кожна заявка розглядається як заявка на один конкретний матеріал. Один і той самий матеріал може бути вказаний у багатьох заявках.

## 2. Приклад вхідного JSON-файлу

```json
[
  {
    "id": 100001,
    "material": {
      "id": 240,
      "name": "Material_66",
      "unit": "METERS"
    },
    "quantity": 69.5,
    "status": "IN_APPROVAL",
    "tags": "heavy, wood"
  }
]

```

---

## 3. Приклад вихідного XML-файлу

```xml
<?xml version="1.0" encoding="UTF-8"?>
<statistics>
  <item>
    <value>heavy</value>
    <count>1</count>
  </item>
  <item>
    <value>wood</value>
    <count>1</count>
  </item>
</statistics>

```

## 6. Генерація тестових даних

Для тестування програми використовується клас `DataGenerator`, який генерує набір JSON-файлів.

Параметри генерації:

| Параметр | Значення |
|---|---:|
| Кількість JSON-файлів | 10 |
| Кількість записів у кожному файлі | 10 000 |
| Загальна кількість записів | 100 000 |
| Кількість можливих матеріалів | 500 |
| Кількість можливих тегів | 7 |
| Кількість тегів в одному записі | 1–2 |
| Кількість статусів | 5 |
| Кількість одиниць вимірювання | 4 |

Для кожного запису випадково генеруються:
- `id`;
- `material.id`;
- `material.name`;
- `material.unit`;
- `quantity`;
- `status`;
- `tags`.

Ідентифікатор матеріалу генерується випадково в діапазоні `0–499`, тому різні заявки можуть посилатися на один і той самий матеріал.

## 8. Запуск програми

Програма підтримує два способи запуску:

1. Інтерактивний запуск через консоль.
2. Запуск із параметрами командного рядка.

* **При інтерактивному запуску** користувач вводить: шлях до папки з JSON-файлами, назву атрибута та кількість потоків.
* **При запуску з параметрами:**
```bash
<шлях_до_папки> <атрибут> <кількість_потоків>

```


*Приклад:* `data tags 4`

---

## 9. Потокова обробка JSON-файлів

Для парсингу використовується Jackson Streaming API. JSON-файли обробляються по одному об'єкту без завантаження всього файлу в оперативну пам'ять.

---

## 10. Багатопотокова обробка

Для обробки файлів використовується `ExecutorService` з фіксованим пулом потоків. Кожен JSON-файл передається на обробку окремому потоку.

Для безпечної роботи зі статистикою в багатопотоковому режимі використовуються `ConcurrentHashMap` та `LongAdder`.

## 11. Результати експериментів

Для порівняння швидкодії було використано тестовий набір даних, згенерований за допомогою класу `DataGenerator`.

У тесті використовувалися:

- **10 JSON-файлів**;
- **10 000 записів** у кожному файлі;
- загалом **100 000 заявок**;
- **500 можливих матеріалів**;
- від **1 до 2 тегів** у кожній заявці;
- 5 можливих статусів;
- 4 можливі одиниці вимірювання.

Для експерименту програма виконувалася з різною кількістю потоків: 1, 2, 4 та 8. В усіх запусках використовувався однаковий набір вхідних даних та однаковий атрибут для формування статистики.

### Результати

| Кількість потоків | Час виконання |
| --- | ---: |
| **1** | 515 ms |
| **2** | 461 ms |
| **4** | 419 ms |
| **8** | 410 ms |

За результатами експерименту збільшення кількості потоків дозволило скоротити загальний час обробки файлів.

Найбільше прискорення спостерігається при переході від 1 до 4 потоків. Перехід від 4 до 8 потоків дає лише незначне покращення результату.

Це пояснюється тим, що після певної кількості потоків додаткове паралельне виконання вже не дає пропорційного приросту продуктивності через накладні витрати на керування потоками, синхронізацію доступу до спільної статистики та обмеження ресурсів системи.

Таким чином, для використаного тестового набору **4 потоки можна вважати оптимальним компромісом між часом виконання та кількістю потоків**, оскільки використання 8 потоків лише незначно покращує результат.

## 12. Unit-тести

Для перевірки основної логіки проєкту реалізовані unit-тести:

* **`JsonStreamParserTest`** - перевірка парсингу JSON-файлів;
* **`StatisticsAggregatorTest`** - перевірка формування статистики та обробки багатозначних атрибутів;
* **`DirectoryProcessorTest`** - перевірка обробки директорії та генерації XML-звіту;
* **`XmlReportWriterTest`** - перевірка формування XML-файлу.
