# Система агрегації статистики за закупівлями (Java Core)

Консольна багатопотокова програма на Java для потокового парсингу JSON-файлів із купівельними заявками, обчислення статистики за вказаним атрибутом та генерації відсортованого XML-звіту.

---

## 1. Опис основних сутностей

Проєкт побудований на принципах об'єктно-орієнтованого програмування та демонструє зв'язок між сутностями:

PurchaseTransaction (Транзакція закупівлі) - основна сутність, що містить інформацію про окрему операцію закупівлі. Поля: `id` (Long), `material` (`Material` - вкладений об'єкт), `quantity` (Double), `status` (`Status` - Enum: DRAFT, IN_APPROVAL, APPROVED, PURCHASED, CANCELED), `tags` (String - текстові теги через кому).
Material (Матеріал) - другорядна сутність. Поля: `id` (Long), `name` (String), `unit` (`Unit` - Enum: KG, PCS, METERS, LITERS), `description` (String).

Зв'язок між сутностями: Багато-до-одного (Many-to-One) - багато транзакцій закупівлі можуть посилатися на один і той самий матеріал. Кожна транзакція містить один конкретний матеріал.

## 2. Приклад вхідного JSON-файлу

```json
[
  {
    "id": 100001,
    "material": {
      "id": 240,
      "name": "Material_66",
      "unit": "METERS"
    },
    "quantity": 69.5,
    "status": "IN_APPROVAL",
    "tags": "heavy, wood"
  }
]

```

---

## 3. Приклад вихідного XML-файлу

```xml
<?xml version="1.0" encoding="UTF-8"?>
<statistics>
  <item>
    <value>heavy</value>
    <count>1</count>
  </item>
  <item>
    <value>wood</value>
    <count>1</count>
  </item>
</statistics>

```

---

## 4. Підтримувані атрибути для статистики

Програма підтримує формування статистики за такими атрибутами:

* `tags`
* `status`
* `unit`
* `material`

---

## 5. Структура проєкту

Проєкт має стандартну структуру Maven-папок. У папці src/main/java/org/example розміщені пакет model з класами сутностей, пакет service з бізнес-логікою (парсинг, агрегація, обробка директорій та запис XML), а також головний клас Main. У папці src/test/java/org/example знаходяться unit-тести для перевірки всіх основних компонентів (DirectoryProcessorTest, JsonStreamParserTest, StatisticsAggregatorTest, XmlReportWriterTest). У корені проєкту розташовані папки data та examples, а також файли конфігурації pom.xml, README.md та .gitignore.

## 6. Генерація тестових даних

Для тестування програми використовується клас `DataGenerator`, який генерує набір JSON-файлів.

Параметри генерації: кількість JSON-файлів складає 10 штук, кількість записів у кожному файлі дорівнює 10 000, що дає загалом 100 000 записів. Використовується 500 можливих матеріалів, 7 можливих тегів (від 1 до 2 тегів в одному записі), 5 статусів та 4 одиниці вимірювання.

Для кожного запису випадково генеруються `id`, `material.id`, `material.name`, `material.unit`, `quantity`, `status` та `tags`. Ідентифікатор матеріалу генерується випадково в діапазоні від 0 до 500, тому різні заявки можуть посилатися на один і той самий матеріал.

## 8. Запуск програми

Програма підтримує два способи запуску:

1. Інтерактивний запуск через консоль (користувач по черзі вводить шлях до папки з файлами, назву атрибута та кількість потоків).
2. Запуск із параметрами командного рядка у форматі: `<шлях_до_папки> <атрибут> <кількість_потоків>`. Наприклад: `data tags 4`.


---

## 9. Потокова обробка JSON-файлів

Для парсингу використовується Jackson Streaming API. JSON-файли обробляються по одному об'єкту без завантаження всього файлу в оперативну пам'ять.

---

## 10. Багатопотокова обробка

Для обробки файлів використовується `ExecutorService` з фіксованим пулом потоків. Кожен JSON-файл передається на обробку окремому потоку. Для безпечної роботи зі статистикою в багатопотоковому режимі використовуються `ConcurrentHashMap` та `LongAdder`.

---

## 11. Результати експериментів

Для порівняння швидкодії використовувався тестовий набір із 10 JSON-файлів по 10 000 записів (загалом 100 000 транзакцій). Для всіх запусків використовувався однаковий набір вхідних даних та атрибут `tags`.

Час виконання склав: для 1 потоку - 515 ms, для 2 потоків - 461 ms, для 4 потоків - 419 ms, для 8 потоків - 410 ms.

Збільшення кількості потоків дозволило скоротити загальний час обробки. Найбільше прискорення спостерігається при переході від 1 до 4 потоків, тоді як 8 потоків дають лише незначне покращення через накладні витрати на керування потоками та синхронізацію. Для використаного тестового набору 4 потоки можна вважати оптимальним компромісом, оскільки перехід від 4 до 8 потоків дає лише незначне скорочення часу виконання.

## 12. Unit-тести

Для перевірки основної логіки проєкту реалізовані unit-тести:

* `JsonStreamParserTest` - перевірка парсингу JSON-файлів;
* `StatisticsAggregatorTest` - перевірка формування статистики та обробки багатозначних атрибутів;
* `DirectoryProcessorTest` - перевірка обробки директорії та генерації XML-звіту;
* `XmlReportWriterTest` - перевірка формування XML-файлу.
